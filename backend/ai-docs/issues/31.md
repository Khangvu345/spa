## Mô tả

Tích hợp **Cloudinary** để upload ảnh dịch vụ. Hiện Service schema CHƯA có trường ảnh — issue này thêm `imageUrl` vào schema + API upload file lên Cloudinary + trả URL để lưu.

**PDF yêu cầu (mục Quản trị viên):** "Upload ảnh dịch vụ qua Cloudinary." → đây là lý do chọn Cloudinary cụ thể, không tự thay bằng giải pháp khác.

**Vì sao đáng làm dù là bonus:** landing page hiện hiển thị danh sách dịch vụ KHÔNG có ảnh → trông sơ sài. Thêm ảnh làm demo "trông hoàn chỉnh" hơn hẳn. Chi phí thấp (gói miễn phí của Cloudinary, SDK sẵn).

**Phạm vi giới hạn:**
- ✅ Thêm trường `imageUrl` vào Service schema (thay đổi nhẹ — chỉ thêm trường tùy chọn)
- ✅ API upload ảnh → Cloudinary → trả URL bảo mật
- ✅ ADMIN gán URL vào service (qua PATCH /services/:id có sẵn)
- ✅ Cấu hình Cloudinary qua ConfigService (env)
- ❌ KHÔNG upload nhiều ảnh/gallery — 1 ảnh/dịch vụ đủ
- ❌ KHÔNG upload ảnh cho entity khác (material, staff avatar) — chỉ service
- ❌ KHÔNG crop/resize phía server — dùng URL biến đổi của Cloudinary nếu cần
- ❌ KHÔNG tự xóa ảnh cũ trên Cloudinary khi đổi ảnh — ngoài phạm vi MVP (chấp nhận rác)

## Nghiệp vụ (User stories)

- **UP-01 Upload ảnh:** ADMIN chọn file ảnh → upload lên Cloudinary → nhận về URL
- **UP-02 Gán ảnh cho dịch vụ:** ADMIN lưu URL vào `service.imageUrl` (qua PATCH /services/:id)
- **UP-03 Hiển thị ảnh:** Landing page + admin service list hiện ảnh từ `imageUrl`

## API

| Method | Path | Mô tả | Auth |
|---|---|---|---|
| POST | `/upload/service-image` | Upload 1 file ảnh → Cloudinary → trả URL | `@Roles('ADMIN')` |

> Gán URL vào service KHÔNG cần API mới — dùng `PATCH /services/:id { imageUrl }` đã có ở #05 (sau khi thêm trường).
> Flow FE: upload trước (nhận URL) → rồi PATCH service với URL đó. 2 bước tách biệt, đơn giản.

## Acceptance Criteria

### A. Thêm field vào Service schema (#05)

```typescript
// service.schema.ts — THÊM 1 field:
@Prop({ default: '' })
imageUrl: string;        // URL bảo mật của Cloudinary, mặc định rỗng
```
- Trường này là tùy chọn, mặc định `''`. Service cũ không có ảnh vẫn hoạt động.
- Cập nhật `CreateServiceDto` + `UpdateServiceDto`: thêm `imageUrl?` (IsString, IsUrl tùy chọn, tối đa 500 ký tự).
- ⚠️ MongoDB schema-less → service cũ tự động có `imageUrl=''` khi đọc, KHÔNG cần migration script. Chỉ cần thêm field vào schema.

### B. Cấu hình Cloudinary

- [ ] `npm install cloudinary` (backend)
- [ ] Thêm vào `.env.example`:
  ```
  CLOUDINARY_CLOUD_NAME=
  CLOUDINARY_API_KEY=
  CLOUDINARY_API_SECRET=
  ```
  > Giá trị thật chia sẻ riêng qua team chat (KHÔNG commit). Tạo account free tại cloudinary.com.
- [ ] `CloudinaryModule` cấu hình qua `ConfigService` (theo mẫu forRootAsync như các module khác)
- [ ] Khởi tạo cloudinary SDK với cấu hình từ env

### C. Upload logic

- [ ] `UploadController.uploadServiceImage()`:
  - Dùng `@UseInterceptors(FileInterceptor('file'))` (multer, NestJS built-in)
  - Validate file:
    - mimetype phải `image/jpeg | image/png | image/webp` → sai 400 UPLOAD_INVALID_TYPE
    - size <= 5MB → quá 400 UPLOAD_FILE_TOO_LARGE
  - Stream buffer lên Cloudinary (folder `spa/services`)
  - Trả `{ url: secure_url, publicId }`

- [ ] `CloudinaryService.uploadImage(file): Promise<{ url, publicId }>`
  - Dùng `cloudinary.uploader.upload_stream` (vì nhận buffer từ multer memoryStorage)
  - Folder: `spa/services`
  - Trả `secure_url` (https) + `public_id`

### D. Module

```typescript
@Module({
  imports: [ConfigModule],
  controllers: [UploadController],
  providers: [CloudinaryService],
  exports: [CloudinaryService],
})
```
> KHÔNG cần MongooseModule — upload không đụng DB. Việc lưu imageUrl vào service do ServiceModule lo qua PATCH có sẵn.

### E. Error Codes (THÊM MỚI vào error-codes.ts)

```typescript
// Upload
UPLOAD_INVALID_TYPE:     'UPLOAD_INVALID_TYPE',
UPLOAD_FILE_TOO_LARGE:   'UPLOAD_FILE_TOO_LARGE',
UPLOAD_FAILED:           'UPLOAD_FAILED',     // Cloudinary trả lỗi
```

## Testing — Acceptance Test Cases

- [ ] POST /upload/service-image với file .jpg hợp lệ → 200, trả secure_url https
- [ ] POST với file .pdf → 400 UPLOAD_INVALID_TYPE
- [ ] POST với file ảnh > 5MB → 400 UPLOAD_FILE_TOO_LARGE
- [ ] POST không kèm file → 400
- [ ] POST từ non-ADMIN → 403
- [ ] Upload xong → PATCH /services/:id { imageUrl } → GET service thấy imageUrl
- [ ] GET /services (public) → service có ảnh trả imageUrl, service cũ trả imageUrl=''
- [ ] Thông tin xác thực Cloudinary sai → 500 UPLOAD_FAILED (không làm hỏng app)

## Context bổ sung từ dev

**Quyết định kỹ thuật đã chốt:**

1. **Tách upload và gán URL thành 2 bước** — upload trả URL trước, rồi PATCH service riêng. Đơn giản hơn gộp 1 API (không phải xử lý multipart + update DB cùng lúc). FE gọi 2 lần.

2. **Thêm field `imageUrl` KHÔNG cần migration** — MongoDB schema-less, service cũ tự có `imageUrl=''`. Đây là lý do Vu để comment sẵn từ #05.

3. **multer memoryStorage** — file vào buffer (không lưu disk), stream thẳng lên Cloudinary. Phù hợp deploy trên môi trường tạm thời.

4. **Không tự xóa ảnh cũ** — đổi ảnh để lại rác trên Cloudinary. Gói miễn phí đủ chứa, MVP chấp nhận. Nếu lo → ghi `publicId` để xóa sau (ngoài phạm vi).

5. **Chỉ service có ảnh** — material/staff không cần ảnh cho demo. Giữ phạm vi hẹp.

6. **Cấu trúc thư mục:** `src/modules/upload/` + `CloudinaryService` bên trong (hoặc `src/shared/cloudinary/` nếu muốn dùng lại). Cấu trúc phẳng là đủ cho MVP.

7. **Lưu ý cho FE:** dùng component Ant Design `Upload`, action trỏ `/upload/service-image`, `onSuccess` lấy `url` → set vào trường form `imageUrl` → submit PATCH service. KHÔNG cần FE đụng Cloudinary trực tiếp (BE proxy).

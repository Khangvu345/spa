## Nội dung Issue (paste nguyên văn)

## Mô tả

Triển khai module **Booking** (Lịch hẹn) — khách đặt lịch qua landing page hoặc OPERATOR tạo thay mặt. Bao gồm logic **Slot Availability** tính giờ trống của chuyên viên (1 trong 4 tính năng rủi ro cao của dự án).

**Phương án UX đã chốt (Phương án C — Hybrid):**
- Khách chọn dịch vụ + ngày → backend trả về **top 8 khung giờ gợi ý còn trống**
- Khách bấm 1 nút → điền vào form
- KHÔNG hiển thị lưới giờ đầy đủ kiểu rạp chiếu phim (giảm độ phức tạp FE)
- OPERATOR có endpoint riêng trả lưới giờ đầy đủ để phân công chi tiết

**Cấu hình đã chốt:**
- Giờ spa: 8:00 — 22:00
- Slot step: 30 phút
- Buffer giữa các booking cùng staff: 15 phút
- OTP TTL: 3 phút (giai đoạn 3, chưa triển khai trong issue này)
- Schema có sẵn fields OTP nhưng **chưa bật logic** — giai đoạn 1 tạo booking status=CONFIRMED ngay

**Phạm vi giới hạn:**
- ✅ Booking CRUD + luồng trạng thái
- ✅ Slot Availability endpoint (customer + operator)
- ✅ Schema có sẵn fields OTP (otpCode, otpExpiresAt, otpAttempts, verifiedAt) — mặc định null
- ✅ Link Booking → Service Order khi check-in
- ❌ KHÔNG triển khai gửi/xác thực OTP — giai đoạn 3
- ❌ KHÔNG triển khai notification (email/SMS confirm) — giai đoạn 3
- ❌ KHÔNG triển khai đổi lịch — ngoài phạm vi MVP (hủy + tạo lại)

**Luồng trạng thái:**
```
PENDING_OTP ──(verify OTP)──→ CONFIRMED ──→ CHECKED_IN ──→ IN_PROGRESS ──→ COMPLETED
       │                          │              │
       │                          ▼              ▼
       └──────────────────────→ CANCELLED ←── NO_SHOW (chỉ từ CONFIRMED)
       └──(OTP expire/3 sai)──→ CANCELLED (auto)
```

**Giai đoạn 1 status mặc định = CONFIRMED ngay** khi tạo (bỏ qua bước OTP). Giai đoạn 3 OTP sẽ đổi mặc định thành PENDING_OTP cho `source=LANDING_PAGE`.

**Indexes cần tạo:**
- `bookingCode` (unique)
- `staffId, scheduledStart` (compound — query slot availability)
- `status` (lọc)
- `customerId` (lọc)
- `scheduledStart` (sắp xếp)
- TTL index trên `otpExpiresAt` với partial filter `status=PENDING_OTP` (giai đoạn 3 sẽ bật — giai đoạn 1 chuẩn bị sẵn)

### C. SlotAvailabilityService (helper, NOT controller)

**Đây là core logic — tách thành service riêng để Booking module và OPERATOR module reuse.**

```typescript
@Injectable()
export class SlotAvailabilityService {
  // Config
  readonly OPEN_HOUR = 8;        // 8:00
  readonly CLOSE_HOUR = 22;      // 22:00
  readonly SLOT_STEP_MINUTES = 30;
  readonly BUFFER_MINUTES = 15;
  
  async calculateSlots(serviceId, date): Promise<SlotInfo[]>
  async getSuggestedSlots(serviceId, date, count = 8): Promise<string[]>
  async getFullGrid(serviceId, date): Promise<SlotInfo[]>
  async isSlotAvailable(serviceId, scheduledStart): Promise<boolean>
}
```

**Logic `calculateSlots`:**

1. Lookup service → get `durationMinutes`, `cleanupMinutes` → `totalBlockTime = duration + cleanup`
2. Lookup staff phụ trách service qua `staff_service_assignments` → 1 staff duy nhất
3. Query bookings của staff đó trong ngày, status IN ['PENDING_OTP', 'CONFIRMED', 'CHECKED_IN', 'IN_PROGRESS']
4. Generate candidate slots từ `OPEN_HOUR:00` đến `CLOSE_HOUR:00` mỗi `SLOT_STEP_MINUTES` (8:00, 8:30, ..., 21:30)
5. Loại bỏ slot không đủ thời gian (`slotStart + totalBlockTime > CLOSE_HOUR`)
6. Với mỗi candidate slot, check overlap với bookings hiện có (kèm buffer 15 phút 2 đầu)
7. Trả về array `[{ time: 'HH:MM', status: 'FREE' | 'BUSY', bookingId? }]`

**Logic `isSlotAvailable`:**

- Gọi `calculateSlots` → check time có trong list FREE không
- Dùng khi POST /bookings để validate trước khi tạo

    - Mạch liên kết: Booking → ServiceOrder → Invoice (linear, không cross)

### Quyết định bổ sung 2026-05-24 - Vòng đời Booking ↔ Service Order

**Chốt bởi:** Vu (tech lead)

- Sau check-in, Service Order là chủ vòng đời phục vụ. Booking đồng bộ theo SO:
  - SO `IN_PROGRESS` → Booking `IN_PROGRESS`
  - SO `COMPLETED` → Booking `COMPLETED`
  - SO `INVOICED` → Booking giữ `COMPLETED`
- Hủy Booking chọn hướng B-controlled: cho phép hủy ở mọi điểm thao tác trực giác, nhưng cascade Service Order có kiểm soát.
- Quy tắc cascade:
  - Booking chưa check-in (`serviceOrderId=null`) → chỉ hủy Booking.
  - SO `DRAFT` hoặc `IN_PROGRESS` → hủy cả SO và Booking trong transaction.
  - SO `COMPLETED` hoặc `INVOICED` → 400 `BOOKING_CANNOT_CANCEL_SERVED`.
  - SO đã `CANCELLED` → chỉ hủy Booking.
- Error code mới: `BOOKING_CANNOT_CANCEL_SERVED`.

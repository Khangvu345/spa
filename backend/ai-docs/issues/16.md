## Nội dung Issue (paste nguyên văn)

## Mô tả

Implement module **Phiếu dịch vụ** (Service Order) — đại diện cho 1 lần khách đến spa sử dụng 1 hoặc nhiều dịch vụ. Phiếu dịch vụ là **cầu nối giữa Booking/Walk-in và Invoice**.

**Workflow nghiệp vụ:**
```
Khách đến spa (đặt lịch trước HOẶC walk-in)
  → OPERATOR check-in (Booking → CONFIRMED → IN_PROGRESS) hoặc tiếp nhận walk-in
  → OPERATOR tạo Service Order (status=DRAFT) với 1+ dịch vụ
  → OPERATOR assign chuyên viên cho từng dịch vụ (theo staff_service_assignments)
  → STAFF thực hiện, OPERATOR cập nhật status=IN_PROGRESS → COMPLETED
  → OPERATOR chuyển sang Invoice (status=INVOICED)
```

**Đây là issue trọng tâm phase 1 của Khang** — gỡ block hoàn toàn cho Khánh code Invoice (#19).

**Phạm vi giới hạn:**
- ✅ CRUD đầy đủ phiếu dịch vụ
- ✅ Thêm/sửa/xóa items (dịch vụ) trong phiếu
- ✅ Status transition validate
- ✅ Snapshot service info (tên, giá) tại thời điểm thêm item
- ✅ Field `extraCharge` (chi phí phát sinh) + `note`
- ❌ KHÔNG tự động tạo Invoice — Khánh làm ở #19
- ❌ KHÔNG liên kết Booking → Service Order auto — Khang sẽ làm ở #17 (Booking)
- ❌ KHÔNG include khái niệm `slot` chi tiết — chỉ lưu `serviceStaffId` snapshot

## Nghiệp vụ (User stories)

- **SO-01 Tạo phiếu:** OPERATOR tạo phiếu khi khách check-in (đã đặt) hoặc walk-in
- **SO-02 Thêm dịch vụ:** OPERATOR thêm service vào phiếu, system snapshot price + commission rate
- **SO-03 Sửa dịch vụ:** OPERATOR sửa số lượng, ghi chú từng item khi phiếu chưa COMPLETED
- **SO-04 Xóa dịch vụ:** OPERATOR xóa item khi phiếu chưa COMPLETED
- **SO-05 Ghi nhận chi phí phát sinh:** Field `extraCharge` (vd: tip, dịch vụ thêm không có giá cố định)
- **SO-06 Xác nhận hoàn thành:** OPERATOR set status=COMPLETED khi staff báo xong
- **SO-07 Chuyển thanh toán:** OPERATOR set status=INVOICED khi Khánh tạo Invoice (Khánh tự transition qua API riêng ở #19)
- **SO-08 Hủy phiếu:** OPERATOR set status=CANCELLED nếu khách hủy giữa chừng
- **SO-09 Xem danh sách:** OPERATOR/ADMIN xem list, filter theo status, customer, date
- **SO-10 Xem chi tiết:** Full info kèm items, customer, total

## Acceptance Criteria

### A. Schema `service_orders` (MongoDB collection: `service_orders`)

```typescript
{
  orderCode: string;          // unique, auto-gen: 'SO-YYYYMMDD-NNNN' (VD: 'SO-20260517-0001')
  
  customerId: ObjectId;       // ref Customer, required
  
  // Embed items (snapshot — KHÔNG ref live)
  items: [{
    _id: ObjectId;            // sub-document id
    serviceId: ObjectId;      // ref Service
    serviceCode: string;      // snapshot
    serviceName: string;      // snapshot
    unitPrice: number;        // snapshot tại thời điểm thêm vào phiếu (VND, integer)
    quantity: number;         // default 1 (phòng trường hợp khách dùng 2 lần cùng dịch vụ)
    subtotal: number;         // unitPrice * quantity
    
    // Snapshot assignment để Invoice tính commission
    staffId: ObjectId;        // chuyên viên thực hiện (từ staff_service_assignments)
    staffName: string;        // snapshot
    commissionRate: number;   // snapshot tại thời điểm thêm (0-100, integer %)
    
    note: string;             // ghi chú riêng cho item
    addedAt: Date;
  }],
  
  itemsSubtotal: number;      // sum(items.subtotal) — tính lại mỗi khi items thay đổi
  extraCharge: number;        // chi phí phát sinh (VND), default 0
  totalAmount: number;        // itemsSubtotal + extraCharge
  
  status: 'DRAFT' | 'IN_PROGRESS' | 'COMPLETED' | 'INVOICED' | 'CANCELLED';
  
  note: string;               // ghi chú chung của phiếu (vd: 'Khách yêu cầu phòng yên tĩnh')
  
  // Audit
  createdBy: ObjectId;        // OPERATOR/ADMIN tạo phiếu
  createdByName: string;      // snapshot
  
  // Liên kết Booking (nếu có) — phase 1 nullable, phase Booking #17 set
  bookingId: ObjectId | null;
  
  // Timestamps quan trọng cho thống kê
  startedAt: Date | null;     // khi status chuyển sang IN_PROGRESS
  completedAt: Date | null;   // khi status chuyển sang COMPLETED
  invoicedAt: Date | null;    // khi status chuyển sang INVOICED (Khánh set)
  cancelledAt: Date | null;
  
  createdAt: Date;
  updatedAt: Date;
}
```

**Status flow:**
```
DRAFT ──→ IN_PROGRESS ──→ COMPLETED ──→ INVOICED
  │            │              │
  └────────────┴──────────────┴──→ CANCELLED (từ bất kỳ status nào trừ INVOICED)
```

**Quy tắc transition:**
- DRAFT → IN_PROGRESS: chỉ khi có ≥1 item
- IN_PROGRESS → COMPLETED: bắt buộc
- COMPLETED → INVOICED: chỉ Invoice module (Khánh #19) set, qua endpoint riêng
- Bất kỳ → CANCELLED: được, trừ INVOICED (đã thanh toán không hủy được)
- Edit items chỉ cho phép khi status = DRAFT hoặc IN_PROGRESS

**Indexes cần tạo:**
- `orderCode` (unique)
- `customerId` (filter — xem lịch sử khách)
- `status` (filter phổ biến)
- `createdAt` (sort)
- Compound `(status, createdAt)` cho query "phiếu chờ thanh toán hôm nay"
- `bookingId` (filter — nullable)

## Context bổ sung từ dev

**Quyết định kỹ thuật đã chốt:**

1. **Items là EMBED sub-document, KHÔNG reference** — vì cần snapshot price/commission tại thời điểm thêm item. Nếu sau này ADMIN sửa giá service, item lịch sử vẫn đúng. Cũng phù hợp snapshot pattern toàn dự án.

2. **Tách `POST /service-orders` (tạo rỗng) và `POST /service-orders/:id/items` (thêm item)** — đơn giản hóa transaction. OPERATOR tạo phiếu rỗng cho khách, rồi từ từ add từng item theo lúc khách chọn.

3. **`orderCode` format `SO-YYYYMMDD-NNNN`** — sequence theo ngày. Implementation: query `countDocuments({ createdAt từ đầu ngày }) + 1`. Có race condition nhỏ → retry 3 lần nếu unique fail (chấp nhận cho MVP). Production-grade nên dùng atomic counter collection.

4. **Status transition chia thành 2 loại:**
   - **Qua PATCH** `/service-orders/:id`: chỉ DRAFT → IN_PROGRESS (vì transition "đơn giản", không cần side effect lớn)
   - **Qua endpoint riêng** (`/complete`, `/cancel`, `markAsInvoiced` internal): các transition có side effect (set timestamp, cần validate phức tạp)
   
   Lý do tách: dễ test, dễ hiểu, audit log rõ ràng.

5. **`commissionRate` snapshot tại thời điểm add item** — đảm bảo Invoice tính commission đúng nếu sau này ADMIN sửa assignment.

6. **Edit items chỉ cho DRAFT + IN_PROGRESS** — khi COMPLETED tức staff báo xong, không được sửa nữa. Nếu cần sửa → CANCEL phiếu rồi tạo phiếu mới.

7. **`bookingId` nullable phase 1** — phase 2 Booking sẽ link khi check-in. Phase 1 walk-in chiếm phần lớn use case.

8. **`extraCharge` có thể âm không?** — KHÔNG cho phép âm trong DTO (`Min 0`). Nếu cần discount → xử lý ở Invoice level (Khánh #19) với field `discount` riêng.

9. **`createdByName` snapshot** — vì OPERATOR có thể bị resign/đổi tên, lưu snapshot để báo cáo lịch sử đúng.

10. **`markAsInvoiced` là internal method có session param** — Khánh inject `ServiceOrderService` vào Invoice service, gọi `markAsInvoiced(orderId, invoiceId, session)` trong cùng transaction với Invoice creation. Đảm bảo nguyên tử.

11. **Folder structure:** `src/modules/service-order/` (flat, kebab-case folder).

12. **Lưu ý cho Khánh — ràng buộc Invoice:**
    - Invoice chỉ tạo được từ Service Order có status=COMPLETED
    - Mỗi Service Order có tối đa 1 Invoice (1-1 relationship)
    - Khi Invoice tạo thành công → Khánh gọi `serviceOrderService.markAsInvoiced(orderId, invoiceId, session)` trong transaction
    - Khi Invoice cancel (nếu có) → Khánh gọi method tương tự để revert status COMPLETED
